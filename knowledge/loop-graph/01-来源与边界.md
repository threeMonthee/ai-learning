## 「我的工作是写循环」出自访谈

「I don't prompt Claude anymore. I have loops that are running. They're the ones that are prompting Claude and figuring out what to do. My job is to write loops.」出自 2026-06 的 Acquired Unplugged 访谈，大约 11:14。同一次谈话里他把这件事放在抽象层级上升的序列上：打孔卡、汇编、高级语言、补全、自己写 prompt、再由循环去写 prompt。他给这个阶段的时间是接下来几个月到这一年，没有把它说成终点。

机制在 Sequoia 的谈话里，大约 7:56。他说 `/loop` 就是让 Claude 用 cron 预约一个会重复的任务，间隔可以是一分钟、五分钟或一天。他点名的循环都是维护类工作：

| 循环 | 成功条件 | 谁来判定 |
| --- | --- | --- |
| 照看 PR：修 CI、自动 rebase | CI 绿、分支已 rebase | CI 和 git |
| 维持 CI 健康，修 flaky test | 测试套件通过 | 测试套件 |
| 每 30 分钟把 Twitter 反馈聚类 | 报告按时出现 | 报告本身，它不改产品 |

他同时说白天大约 5 到 10 个会话、几百个 agent，夜里几千个做更深的工作。夜里那些 agent 的例子仍然是上面这种能被机器检查的工作。

Routines（`/schedule`）是同一模式搬到云上，笔记本合上还在跑。Simon Willison 在 2026-05 Code with Claude 的记录里写，Anthropic 把 Routines 称为 higher-order prompts。

## 官方怎么定义 loop

Claude Code 团队的文章 [Getting started with loops](https://claude.com/resources/articles/getting-started-with-loops)（Delba de Oliveira、Michael Segner）把 loop 定义成：agent 重复一轮工作，直到停止条件成立。他们按触发和停止分成四类：

| 类型 | 触发 | 停止 | 产品里的抓手 |
| --- | --- | --- | --- |
| Turn-based | 人发一条 prompt | 模型认为做完了，或它缺上下文 | 一次对话；用 Skill 把人的检查写进去 |
| Goal-based | 人在当场发 | 目标达成，或轮数到顶 | `/goal`，另有一个模型检查停止条件是否真的成立 |
| Time-based | 时间间隔 | 人取消，或外部事情结束（PR 合并、队列空了） | `/loop` 在本机；`/schedule` 在云上 |
| Proactive | 事件或日程，当场没有人 | 每一项达到自己的目标；例程一直开到人关掉 | 上面几项再加上 dynamic workflows、auto mode |

同一篇文章要求：循环要有清楚的成功条件和停止条件；确定性的步骤用脚本，不要让模型重新推导；先在一小片工作上试，再放量。

[Building verification loops](https://claude.com/resources/articles/building-verification-loops-in-claude-code-with-skills) 把验证定义成模型在回复之前检查自己的工作。模型已经能看见类型检查、lint、测试和运行错误。人还在手工做的那几步，写成 Skill，循环才能自己关上。

## 社区后来补上的两层名字

Addy Osmani 在 2026-06-08 的文章里把这件事命名为 loop engineering：你不再当那个给 agent 发 prompt 的人，你设计那个会发 prompt 的系统。他按触发把循环分成 heartbeat、cron、hook、goal。这四类和 Claude Code 的四类能对上，只是切分角度不同：一个按产品原语，一个按调度方式。

Graph engineering 描述的是编排。节点可以是 agent、一次模型调用、一段确定性代码，或一个人。边是转移，边上有条件。David Khourshid（XState 的作者）的说法最干净：一个 loop 就是一张有向有环图，上面只有一个节点，边指回自己。Graph 是把其余节点画出来。

LangChain 的表述也站得住：loop 是 graph 的简单形态。PALO IT 在 [Beyond the Harness](https://www.palo-it.com/en/blog/loop-and-graph-engineering) 里把两者都放回 harness 里面，并给出该升级成图的三个条件：专家 agent 之间的条件路由、必须能跨重启恢复的长状态、需要单独测试的路径。

Anthropic 在 2024-12 的 *Building effective agents* 里已经画过同一条线：控制流写在代码里的是 workflow，模型自己决定下一步的是 agent。能用单循环加传感器解决的，就不要先画图。模型变强之后，写死的分支会变成要维护、最后要删掉的代码。

## 做企业实验时采用的定义

后面的教程固定用这几个词：

- **目标**：这一次运行结束时，世界上哪个事实要为真。
- **努力**：轮数、金额、允许改哪些路径。到了就停，不靠模型自己觉得「差不多了」。
- **验证**：一个不看模型自述、只看证据的判定。测试、HTTP 状态、审计日志、截图对比都算。模型说「我做完了」不算。
- **Loop**：外层重复。它发现工作、启动一次运行、看停止条件、决定再来还是停。
- **Graph**：一次运行内部的控制流。节点做事，边决定下一步，闸门和人是节点。
- **Skill**：把「怎样验证、怎样建、哪些文件要读」写成可复用的说明和脚本。它不是每一轮都重写的 prompt。

自改进循环（跑完一次就改自己的提示或路由）不在这次实验里。公开材料里它还是说法，缺少可核对的停止条件和审计方式。企业里第一次实验先把「人能看懂的证据」跑通。
