# 企业内实验教程

目标：在做企业内部应用的一个版本需求时，用 loop 加 graph 跑这一张工单，看清楚它在哪停下、证据够不够让人在几分钟内做决定。实验结束时你们要留下可复用的运行时和一张真实工单的审计日志，而不是一套新口号。

实验范围是一张工单、一个功能分支、一条不会自动合并的图。生产发布、权限变更、客户数据迁移不进这张图。

## 0. 选定那一张工单

用第 2 篇里的验证梯子筛选。合适的第一张工单同时满足：

- 有一个写得清的业务事实，例如「提交满 30 分钟后再撤回，接口返回 409，并写下审计事件」。
- 这个事实能变成测试、接口断言或日志查询。
- 改动落在一个团队熟悉的服务里，审查者看得懂 diff。
- 做完不需要当天上生产。人批准之后仍然走你们原有的合并流程。

「把体验做好一点」「顺一下那个页面」先不要进。参考实现里这种工单会在 `checkable` 闸门停住，走到人节点，实现节点的进入次数是 0。这是正确行为，可以当成对照样本跑一次，确认闸门真的会拒绝。

下面用一张符合条件的例子贯穿全篇：请假单提交后 30 分钟内可撤回。代码里的对应物是 `withdrawTicket`。

## 1. 把目标、努力、验证写成三行

在工单正文顶部写，不要写在聊天里：

```text
目标：员工提交请假后 30 分钟内可撤回；超时调用撤回接口返回 409；成功撤回写一条含操作者和单号的审计事件。
努力：最多 12 轮、实现节点最多进入 2 次、只允许修改 src/leave/** 和对应测试；不合并、不部署。
验证：测试断言 409 和审计事件。缺任何一条，verify 为失败。人只看证据包，不看模型的完成声明。
```

这三行对应 Cherny 2026-10-06 帖子里的三件事。第三行必须是程序能读的。如果写不出来，这张工单还不能进循环，先回到写验收项。

## 2. 把验收项收成数据

每一项一个 id、一种判定、一句话。

```ts
checks: [
  { id: "reject-after-window", kind: "machine", detail: "超过 30 分钟调用撤回，返回 409" },
  { id: "audit-event", kind: "machine", detail: "成功撤回时审计日志出现 withdraw，含操作者和单号" },
]
```

`kind: "human"` 表示目前没有程序能判定它。闸门看到任何一条 human，就把整张工单送到人那里，并在证据里写明是哪些 id。不要让实现节点「先做一版看看」。

收验收项的 agent 只做这一件事。它不改代码。它的输出就是 `checks` 数组。

## 3. 按节点实现，先用假的实现把边跑通

控制流和模型能力是两件事。先把边跑通，再把 agent 节点换成真正的模型调用。参考目录就是这一步：

```bash
cd knowledge/loop-graph/reference
npm test
```

四个测试锁住这些行为：

- 可验证工单第一次实现故意漏掉最后一条验收项，验证失败后沿 `retry-while-budget-remains` 回来，第二次补齐，然后生成证据包并停在人节点。实现节点进入 2 次。
- 人批准后，运行到 `done`，花费不超过预算。
- 「体验更好」这种工单不到达实现节点。
- 人拒绝后，最后一条边的 guard 是 `human-rejected`，状态是失败，日志还在。
- 外层 `heartbeat()` 对队列里的每张新工单启动一次运行，两张都停在待审，没有一张被自动完成。

假的实现节点用进入次数决定补丁覆盖了哪些验收项。换成真实模型时，删除这个假逻辑，保留闸门。闸门继续只读 `patch.satisfied` 和测试命令的退出码，不读模型的自我评价。

真实的实现节点建议收成这个函数签名：

```ts
run(state): Promise<{
  usd: number
  artifacts: { patch: { summary: string; files: string[]; satisfied: string[] } }
  evidence: { ok: boolean; summary: string }
}>
```

`satisfied` 不是模型自己填的。它由后面的 `verify` 闸门根据测试结果填写，再写回状态。模型填写的「我覆盖了」只能出现在 summary 里，不能出现在闸门读取的字段里。参考实现为了不依赖测试进程，暂时让假补丁自带 `satisfied`。接到真实仓库时把这两件事拆开。

## 4. 验证闸门只跑命令和比较

闸门内部做三件事：

1. 在功能分支上跑你们已经写好的测试命令。退出码非 0 就是失败。
2. 把失败用例映射回验收项 id。映射写在测试名字或断言消息里，例如 `audit-event`。
3. 读 diff，确认这次为了变绿没有删掉或放宽已有断言。Claude 的 verification skill 课程把这一步放在「测试绿了」之后，因为放宽测试是最常见的假通过。

失败时证据的 summary 写缺少的 id，例如 `缺少 audit-event`。下一次实现节点只能看到这份证据和工单，不要把上一轮的长推理塞回上下文。

## 5. 证据包要能在手机上看完

Cherny 说他后来很多工作在手机上的 Claude app 里看会话。这只有在输出是通过或失败、并且理由是一句话时才成立。证据包固定这几段，长 diff 用链接，不贴进包里：

- 目标的那一句话。
- 改了哪些文件。
- 每条验收项：id、命令、通过或失败、一行输出。
- 花了多少轮、多少金额。
- 要人回答的一个问题：「按证据包决定能否合入」，或「验收项还不能由机器判定，退回或拒绝」。

人的回复只有批准或拒绝，加一句注记。注记进入审计，不进入路由。路由只看布尔值。

## 6. 接到你们的队列上

第一周不要上 cron。人在工单进入「就绪」列时手动调用一次 `heartbeat()`。看三张工单的日志：一张清晰的、一张故意含糊的、一张会失败的。含糊的必须停在闸门。失败的必须在两次实现后停给人，而不是第三次继续改。

第二周再把 `heartbeat()` 挂到已有调度器，间隔先用 30 分钟或 1 小时，对齐「外部状态多久变一次」，而不是对齐模型有多快。Claude Code 文档里的原话是不要跑得比被观察的东西变得更勤。

调度器只调用心跳。心跳发现状态是 `needs_human` 的运行时不要再次 `drive()`。参考实现用运行 id 记住已经启动过的工单。

## 7. 权限和审计

在企业环境里把下面几条写成运行账号的权限，而不是写成 prompt：

- 运行账号不能合并到默认分支，不能部署，不能读生产密钥。密钥若出现在工具输出里，这一轮作废并告警。
- 每个节点的工具列表不同。intake 只有读工单。implement 只有功能分支的写。verify 只有测试命令和只读 git。
- 审计日志和证据包写到工单系统，保留运行 id、guard 名字、花费。出了问题用日志复盘，不靠聊天记录。
- 同一次运行只保留一个写者。并行 worktree 是以后的事。公开材料里不同 agent 的 PR 冲突率明显高于同一个 agent 的连续 PR，第一次实验不引入这个变量。

## 8. 怎样判断这次实验成了

跑完一周，只看这四项。四项都成立，才把第二张工单放进同一张图。

1. 含糊工单没有产生 diff。
2. 清晰工单的证据包里，每条验收项都有命令和结果。审查者没有回头让模型「再解释一下」。
3. 失败时日志里能指出停在哪条 guard，并且实现次数没有超过上限。
4. 花费在预算内。超预算的运行状态是 `budget_exhausted`，不是「差不多做完了」。

任何一项不成立，改的是验收项、闸门或预算，不是把 prompt 写得更长。

## 9. 什么时候才往图上加节点

当前这张图只有一条实现路径。出现下面任一情况再加节点，一次加一个，并给新边写测试：

- 缺陷和需求要走不同的专家步骤，下一步取决于上一个节点的结构化输出。
- 运行会超过你们进程的生命周期，必须把 `RunState` 存下来，重启后从游标继续。
- 某条失败边需要单独测试，不能靠把整张图跑一遍来覆盖。

在这之前，把时间花在传感器上：测试、lint、日志查询、diff 检查。Anthropic 对 workflow 和 agent 的建议，以及 PALO IT 对 loop 和 graph 的建议，都是这一条。

## 10. 对照：如果你们直接用 Claude Code 做同一张工单

不想先写运行时的团队，可以在 Claude Code 里做同一实验，职责保持一致。

1. 把第 1 节的三行写进仓库里的 `SKILL.md`，名字用 `verify-leave-withdraw`。正文列出测试命令、审计日志要出现的字段、失败后从测试重跑，不要从「我觉得好了」重跑。
2. 对人说目标，像对同事说那张工单，不要把三十条格式要求叠进开场白。格式要求放在 Skill 和测试里。
3. 用 `/goal` 写停止条件，并写上轮数上限。例如：撤回接口的两条断言都绿，最多 5 轮。
4. 实现和检查分开会话。检查会话只拿 diff、测试输出和 Skill。
5. 人看证据包再走原有的 PR 评审。不要开 auto mode 让它自己合并。

`/loop` 先用在只读检查上，例如每小时看一次这条 PR 的 CI 是否变红并把失败摘要写回工单。CI 绿了只是报告，不是合并。
