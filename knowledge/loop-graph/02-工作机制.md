# 工作机制

## 两层，不要混成一个词

外层是 loop，内层是 graph。

```text
heartbeat / cron / hook
        │
        ▼
   取出一张工单
        │
        ▼
┌──────────────────────────────────────┐
│ graph run                            │
│                                      │
│  intake → checkable?                 │
│              │是                     │
│              ▼                       │
│         implement ⇄ verify           │
│              │过                     │
│              ▼                       │
│           packet → human → done      │
│                                      │
│  任何一条边都可以通向 human 或 stop   │
└──────────────────────────────────────┘
        │
        ▼
  记录状态，等待下一次触发
```

外层不关心补丁写得对不对。它只负责「有没有新工作、这一次运行现在处于哪个状态」。内层不关心自己是被定时器叫醒的还是被人点的。它只负责把一张工单从入口走到停止。

一个只有「做完再检查，不行就回到做」的流程，就是图的特例：两个节点，一条前进边，一条有次数上限的回边。企业实验可以直接从这张小图开始，外层先用手动点击代替定时器。定时器是验证稳定之后再加的。

## 一次运行里固定的六样东西

1. **工单**：人写的原始需求。运行过程中不改它，改写后是一张新工单。
2. **验收项**：从工单收出来的检查列表。每一项标明 `machine` 或 `human`。
3. **产物**：计划、补丁、测试输出、证据包。按名字放在运行状态里，后一个节点只读前一个节点写下的名字。
4. **证据**：每个节点追加一条 `{节点, 是否通过, 一句话}`。证据只追加，不改写历史。
5. **预算**：最大轮数、最大金额、允许进入写节点的次数。预算是停止条件的一部分。
6. **审计日志**：每一次跳边记下 `from`、`to`、`guard`。出了问题先读日志，再读模型输出。

参考实现里这些字段就是 `RunState`：`knowledge/loop-graph/reference/src/types.ts`。

## 节点只有四种

| 种类 | 谁在里面 | 允许做的事 | 不允许做的事 |
| --- | --- | --- | --- |
| agent | 模型，带着工具 | 读状态，写它负责的产物 | 自己宣布整个流程结束 |
| gate | 确定性程序 | 读产物，写通过或失败 | 调用模型，改业务代码 |
| tool | 确定性程序 | 生成证据包、跑测试命令、落库 | 解释「大概是对的」 |
| human | 人 | 看证据包，批准或拒绝 | 在节点内部改代码 |

闸门必须是程序。如果「通过」要靠另一个模型说了算，那个模型是另一个 agent 节点，它的输出还要再经过一个只看结构化字段的闸门。否则失败时无法区分是产品错了还是评审模型嘴软。

人节点会把运行停在 `needs_human`，并带上一个小包：要人回答的那一个问题、目标、证据列表、已经花掉的预算。恢复运行时只接收 `{approved, note}`。人的句子写进证据，跳边只看 `approved`。

## 边是有顺序的条件

从一个节点出发的边按书写顺序匹配，第一条为真的边生效。所以「通过」写在「重试」前面，「重试」写在「次数用尽，交给人」前面。条件要互斥，或者故意按优先级覆盖。

参考图里验证之后的三条边是：

1. `evidence-passed`：验收项全部被补丁覆盖，去生成证据包。
2. `retry-while-budget-remains`：还有缺项，并且实现节点的进入次数还没到上限，回到实现。
3. `retries-exhausted`：还有缺项，次数已经到顶，去人那里，不再自动改代码。

回边如果没有次数上限，就不是循环，是泄漏。实现上用 `maxEntries` 再挡一层：边上的条件写错时，节点进入次数会先把运行打成失败。

## 停止条件谁说了算

模型可以请求停止。停止是否成立，由运行时看三件事：

- 有没有走到名为 done 的终点，而且路上的闸门是通过的。
- 预算（轮数或金额）是否已经越过。
- 人是否拒绝，或者验收项里还有 `human` 种类、根本不该开始写代码。

Claude Code 的 `/goal` 用另一个模型来检查「人写的停止条件是否成立」。企业运行时可以沿用这个办法，但那个检查模型只能返回结构化结论，例如 `{met: boolean, missing: string[]}`，由闸门读取 `met`。不要让检查模型和实现模型共用同一段自我辩解。

## 努力要写成预算，不要写成形容词

Cherny 说的 effort，在系统里是数字和权限：

- 这张工单最多 12 轮、2 美元。数字按你们的模型和单价改，实验开始时就写死。
- 实现节点最多进入 2 次。第二次仍失败就停给人，不继续烧。
- 写权限只开到功能分支。合并、发生产、改权限系统不在这张图里。
- 第一次实验的 agent 只能改工单点名的目录。

「多努力一点」如果只写在 prompt 里，运行时无法在账本里看到它。轮数和金额可以在每次心跳的报告里加总。

## 验证成本决定这张工单能不能进循环

Blake Crosley 对照 Cherny 点过名的循环之后，把任务按「谁来验证、要花多少」排成一架梯子。企业实验用同一架梯子决定一张工单进不进自动运行：

| 工作 | 验证者 | 可否无人值守 |
| --- | --- | --- |
| 只读巡检、生成报告 | 报告本身，不改系统 | 可以，先做这个 |
| 已有测试的重跑、rebase、依赖锁定后 CI 仍绿 | CI | 可以 |
| 带有失败复现的缺陷 | 先写好的复现测试 | 可以，但实现和检查分开 |
| 新功能，验收项能写成测试或接口断言 | 这些断言，再加上人看证据包 | 循环可以写，合入必须等人 |
| 只有「体验更好」「顺一下」的需求 | 人读 diff | 不进入写代码的节点 |
| 权限、资金、生产数据迁移 | 人，而且通常要更长的评审 | 不放进这张图 |

梯子的用法：先看第二列。难但能被测试判定的缺陷，排在容易但只能靠人感觉的文案前面。

## 写循环和读循环分开

只读循环需要的是日程。它拉取状态、对照期望、把 PASS/FAIL 写进报告，没有写权限。

会改仓库或配置的循环，在获得日程之前要有两样东西：顺序约束，以及爆炸半径。顺序约束例子是「先看到部署完成的健康检查，才允许清缓存」。爆炸半径例子是「这个循环只能新建它自己的 worktree，不能删除它没创建的目录」。Crosley 记录过两个事故：自动清理 worktree 时删掉了不是它创建的目录；清缓存跑在部署前面，爬虫拿到了 11 小时的 404。两次都不是模型不会写代码，是写权限给早了。

## 外层心跳长什么样

心跳做四件事：

1. 读队列。已经有运行记录的工单跳过，避免两个循环同时改同一份状态。
2. 为新工单创建一次 graph run，用同一份预算。
3. 把跑到 `needs_human` 的工单放进待审列表。待审列表是给人看的，不是另一段 prompt。
4. 把 `done` 和失败分开计数。失败包含预算用尽、边没匹配上、人拒绝。

参考实现是 `heartbeat()`：`knowledge/loop-graph/reference/src/runtime.ts`。它故意不包含 cron。实验的第一周用手动调用，第二周再把它挂到你们已有的调度器上。调度器挂上之后，循环的正文仍然是这一份。

## 和 Claude Code 原语的对应

如果实验环境就是 Claude Code，不必先重写一个运行时。把上面的角色套进现成原语：

| 这篇笔记里的角色 | Claude Code |
| --- | --- |
| 验收步骤 | `SKILL.md`。描述里写明何时启用，正文写检查命令和失败后从哪一步重跑 |
| 当场迭代到条件成立 | `/goal`，带上轮数上限 |
| 本机重复 | `/loop 5m ...`。机器关掉就停 |
| 合上笔记本还要跑 | `/schedule` |
| 实现和检查分离 | 写代码的会话不复用为评审；用另一个 subagent 或 `/code-review`，打开一份新的上下文 |
| 并行方案 | dynamic workflows。先在一张工单上试，再增加并行 |

产品原语负责单次会话里的循环。跨工单的队列、预算账本、人审的证据包，仍然要落在你们自己的系统里。参考实现补的是这一层，它不替代 Claude Code。

## 运行时每一步实际做什么

`step()` 的顺序是固定的，测试锁住了跳边顺序：

1. 若状态不是 `running`，直接返回。人还没批的运行不会自己继续。
2. 把当前节点的进入次数加一。超过 `maxEntries` 就失败。
3. 轮数或金额已经越过预算，就停，不再调用节点。
4. 执行节点。agent 可以写产物；gate 只写判定。
5. 把证据追加到列表末尾。
6. 如果节点要求暂停，状态改为 `needs_human`，游标留在这个人节点上。
7. 否则按边的书写顺序找第一条成立的边，记下 guard 名字，把游标移过去。
8. 没有边，或者转移前后状态签名完全一样，就失败。后者用来抓住「没有消耗预算也没有移动」的死循环。

人提交决定时不重新执行人节点。`resume()` 把 `{approved, note}` 写进产物，再从人节点出发选边。批准走向 `done`，拒绝走向 `stop`。
